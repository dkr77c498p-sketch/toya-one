# TOYA One 販売用 — 独立環境の準備版

既存の社内用アプリから切り離すためのソース一式です。未公開・接続先未設定です。既存の社内用 main ブランチとデータベースは変更していません。

- 社員名、社員メール、登録済み車両・重機・運搬会社、会社固有の印刷情報を初期値から除外。
- 会社・社員・車両・重機は購入した会社が登録。
- 日報 / 日報＋請求書 / 日報＋請求書＋見積書の3プラン。
- 販売用のログイン保存と会社別ブラウザ保存を専用名に分離。
- 社内用データベースへの接続を拒否。独立した設定が入るまでは準備中画面を表示。
- データベース定義だけを用意。顧客、社員、日報、請求書、写真、登録マスターの実データは含めません。

## 公開までの作業

1. Supabase の管理組織と新規プロジェクトの費用を確認して、販売用の新規プロジェクトを作成する。既存プロジェクトを再利用しない。
2. 新しい空のプロジェクトで `infrastructure/bootstrap.sql` を適用する。既存会社・認証ユーザー・写真がある場合は適用を拒否する。社内用には実行しない。
3. 販売用の新しいリポジトリと公開URLを用意する。この準備ブランチの作業ツリーだけを移し、社内用リポジトリの過去の履歴やバックアップを配布しない。
4. `docs/sales-config.js` に新しい Supabase URL、publishable key、販売用公開URL（末尾 /）を設定する。service_role/secret key はブラウザに置かない。
5. 新しいプロジェクトの Auth の Site URL と許可するリダイレクトURLを販売用に設定する。所有者メール確認とパスワード復旧を実機で検証する。
6. 新しいプロジェクトに `supabase/functions/employee-admin` を配置する。`SALES_APP_ORIGIN` は販売用公開先の origin に設定する。管理者権限・会社契約・端末確認はサーバー側で行う。
7. 新規登録手順から「TOYA試用会社」を作成する。社内用の利用者やデータをコピーしない。試用会社にも通常の販売用契約を設定し、internal フラグを付けない。
8. 3プランの権限、別会社間の遮断、社員IDログイン、端末解除、見積・請求書の保存・印刷を新環境で検証してから公開する。

現時点で新しい保存先・公開URL・試用アカウントは未作成です。組織確認と費用確認が必要です。新しいGitHubリポジトリ作成は現在の接続ツールでは実行できません。この準備ブランチは社内用の公開 main へ統合しないでください。

## 検証

`node tests/sales-boundary.cjs` : JS・HTML構文、参照ファイル、社内DB接続拒否、会社別保存、固有情報、空DBガード。

`tests/sales-browser.cjs` : Playwright と @sparticuz/chromium が必要。スマホ幅390pxで3つの入口を確認。設定未完了時は入力画面を出さず、DB通信は発生しない。

スキーマの実行、実サービスでの認証・権限、実機確認は新しいプロジェクト作成後に行います。未実施の検証を完了扱いにしないでください。

`tools/build_schema.py` は行データを含まないカタログ定義から bootstrap を再生成します。
